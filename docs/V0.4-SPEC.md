# ProofX Protocol v0.4 — Execution Proof Model

**Status:** RC (v0.4.0-rc2)
**Date:** 2026-08-22
**Supersedes:** v0.3 (proof format "1.0")

---

## 1. Overview

ProofX v0.4 extends the cryptographic foundation of v0.3 with an **execution-centric evidence model**. A proof now describes not just what evidence exists, but how evidence relates to each other, what claims it supports, and how those claims are bound cryptographically.

**Core principle:** Evidence → Relations → Claims → Commitment → Signature → Proof

**Design constraints:**
- Backward compatible: v0.4 verifiers MUST accept v0.3 proofs
- v0.3 verifiers MUST reject v0.4 proofs (via version gate)
- No policy engine in v0.4 (deferred to v0.5)
- No external integrations in v0.4 (deferred to v0.6)

## 3. Execution Object

The execution represents the complete CI/build run that produced the evidence.

```jsonc
{
  "id": "string",          // unique execution identifier
  "type": "string",        // "ci-workflow", "local-build", "agent-run", "custom"
  "startedAt": "string",   // RFC3339 timestamp
  "completedAt": "string", // RFC3339 timestamp
  "environment": {
    "os": "string",        // "ubuntu-24.04"
    "arch": "string",      // "amd64", "arm64"
    "runtime": "string",   // "go1.26.5", "node-24.18.0", "python-3.9"
    "tools": [             // optional: additional build tools
      { "name": "string", "version": "string" }
    ]
  }
}
```

**Execution types (extensible):**
- `ci-workflow` — GitHub Actions, GitLab CI, etc.
- `local-build` — Developer machine
- `agent-run` — Autonomous agent execution
- `custom` — Anything else

## 4. Evidence Node (v0.4 enriched)

Same structure as v0.3, with additional optional fields:

```jsonc
{
  "id": "string",          // node identifier (unique within proof)
  "type": "string",        // "git" | "artifact" | "dependencies" | "tests" | "environment" | "custom"
  "source": "string",      // human-readable source description
  "timestamp": "string",   // RFC3339
  "payload": "string",     // canonical JSON string of domain data
  "digest": "string",      // 64-hex SHA-256 of domain-separated payload
  // NEW optional fields:
  "metadata": {},           // arbitrary key-value pairs for display
  "artifactType": "string" // optional: "binary", "image", "sbom", "report"
}
```

**Digest computation (unchanged from v0.3):**
```
digest = hex(sha256("proofx/evidence/v1\x00" + id + ":" + compactJSON(payload)))
```

**Design decision — `type` is NOT committed:**
The evidence digest commits only `id` and `payload`. The `type` field is metadata
(classification label) and is NOT included in the canonical hash. Consequences:

- Mutating `type` alone does NOT invalidate verification.
- This is intentional: `type` is a hint for tooling/CLI display, not a binding commitment.
- The binding root commits the evidence digest, so all payload mutations ARE caught.
- If `type` gains semantic significance in a future version, it can be added to the
  canonical payload in a new domain label (e.g. `proofx/evidence/v2`) without breaking
  v0.1/v0.4 compatibility.

**Test coverage:** Tamper matrix confirms 27 mutation cases all invalidate verification.
`evidence[].type` is intentionally excluded — it is not a committed field.

## 5. Relations

Relations describe how evidence nodes, claims, and the execution connect to each other.

```jsonc
{
  "id": "string",          // unique relation identifier
  "from": "string",        // source node/claim ID
  "to": "string",          // target node/claim ID
  "kind": "string",        // relation type (see below)
  "metadata": {}           // optional: additional context
}
```

**Relation kinds:**

| Kind | From | To | Meaning |
|------|------|----|---------|
| `produces` | execution | evidence | Execution produced this evidence |
| `depends_on` | evidence | evidence | Evidence B requires evidence A |
| `supports` | evidence | claim | Evidence supports this claim |
| `derived_from` | evidence | evidence | Evidence B is derived from A |
| `evaluates` | claim | evidence | Claim evaluates specific evidence |
| `signed_by` | proof | signature | Proof is signed by this signature |
| `binds` | binding | evidence | Binding commitment covers this evidence |

**Constraints:**
- Every evidence node MUST have at least one incoming relation from execution or another evidence node
- Every claim MUST have at least one incoming `supports` relation
- Relations MUST NOT form cycles (except through the proof object itself)
- Relation IDs MUST be unique within the proof

## 6. Claims

Claims are structured assertions about the execution, backed by evidence.

```jsonc
{
  "id": "string",          // unique claim identifier (e.g., "claim.tests_passed")
  "type": "string",        // claim type (extensible)
  "subject": "string",     // what this claim is about (e.g., "execution:exec-001")
  "statement": "string",   // human-readable claim text
  "status": "string",      // "pass" | "fail" | "pending" | "not_applicable"
  "supportedBy": [         // evidence IDs that support this claim
    "string"
  ],
  "evaluatedAt": "string", // RFC3339 timestamp
  "metadata": {}           // optional: additional context
}
```

**Claim types (built-in):**

| Type | Statement | Supports |
|------|-----------|----------|
| `tests_passed` | "All tests passed successfully" | test evidence |
| `artifact_integrity` | "Artifact digests match expected values" | artifact evidence |
| `execution_bound` | "Execution is bound to the specified commit" | git + execution evidence |
| `dependencies_verified` | "Dependency digests are recorded" | dependency evidence |
| `environment_recorded` | "Build environment is documented" | environment evidence |

**Custom claims:** Users can define custom claims in `proofx.yaml`:
```yaml
claims:
  - type: security_scan_passed
    statement: "No critical vulnerabilities found"
    supportedBy:
      - security-scan
```

**Claim status semantics:**
- `pass` — Claim is supported by verified evidence
- `fail` — Evidence contradicts the claim
- `pending` — Claim exists but evidence not yet evaluated
- `not_applicable` — Claim is irrelevant to this execution

## 7. Binding (v0.4 enriched)

The binding now includes relations in the Merkle root computation.

```
v0.3 binding:
  entries = evidence digests only

v0.4 binding:
  entries = evidence digests + relation digests + claim digests
```

**Entry computation:**
```
evidence_entry  = {id: ev.id, digest: ev.digest}
relation_entry  = {id: rel.id, digest: sha256(compactJSON({from, to, kind}))}
claim_entry     = {id: cl.id, digest: sha256(compactJSON({type, subject, statement, status, supportedBy}))}
```

**Root computation:** Same Merkle tree algorithm as v0.3, applied to the combined sorted entries.

**Domain label:** `"proofx/leaf/v2\x00"` (bumped from v1)

---

## 8. Signature (v0.4 enriched)

The commitment digest now includes execution, relations, and claims.

```
commitmentDigest = hex(sha256(
  proofVersion       ‖\x00
  project.name       ‖\x00
  project.repository ‖\x00
  subject.commit     ‖\x00
  subject.branch     ‖\x00
  subject.repository ‖\x00
  execution.id       ‖\x00
  execution.type     ‖\x00
  execution.startedAt ‖\x00
  execution.completedAt ‖\x00
  claim[0].id        ‖\x00  claim[0].type ‖\x00  claim[0].statement ‖\x00  claim[0].status ‖\x00  ... ‖\x00
  binding.algorithm  ‖\x00
  binding.root
))
```

**Signing payload (unchanged structure, new domain label):**
```
signedPayload = "proofx/sign/v2\x00" + commitmentDigest
```

## 9. Coverage (v0.4 enriched)

Coverage now tracks three dimensions:

```jsonc
{
  "evidence": { "total": 12, "verified": 12 },
  "relations": { "total": 17, "verified": 17 },
  "claims": { "total": 4, "verified": 4 },
  "score": 100  // overall: min(evidence, relations, claims)
}
```

8. All evidence, relations, and claims are bound in a Merkle root.

The supplied claims are cryptographically bound to the supplied evidence.
The proof establishes that these claims were made about this execution
and are supported by the referenced evidence.

ProofX does not independently establish that the claims are
semantically true beyond the captured evidence. It proves
integrity, binding, and declared semantics — not absolute truth.

## 11. Backward Compatibility

### v0.4 verifier accepts v0.3 proofs

When `proofVersion == "1.0"`:
- Skip execution, relations fields (treat as absent)
- Claims: use v0.3 format (id, text, status) → map to v0.4 internally
- Binding: use v0.3 entries (evidence only)
- Signature: use v0.3 domain labels (`proofx/leaf/v1`, `proofx/sign/v1`)
- Coverage: compute v0.4 coverage from v0.3 data

### v0.3 verifier rejects v0.4 proofs

`ParseProof` already rejects `proofVersion != "1.0"`. v0.4 sets `proofVersion = "2.0"`, so v0.3 verifiers naturally reject it.

### Migration path

```
v0.3 proof → v0.4 verifier: auto-converted, fully verified
v0.4 proof → v0.3 verifier: rejected with clear error
v0.3 proof → v0.3 verifier: unchanged
v0.4 proof → v0.4 verifier: full verification
```

## 12. Schema Changes

### proofx.yaml v0.4

```yaml
version: "2.0"

# Existing (unchanged)
project:
  name: my-project
  repository: https://github.com/org/repo

# Existing (unchanged)
evidence:
  - git
  - artifact
  - environment
  - tests
  - dependencies

# ENRICHED: claims with structure
claims:
  - type: tests_passed
    statement: "All tests passed successfully"
    supportedBy:
      - tests
  - type: artifact_integrity
    statement: "Artifact digests match expected values"
    supportedBy:
      - artifact

# NEW: execution context
execution:
  type: ci-workflow
  # environment auto-detected, overrides optional
```

### proof.schema.json v0.4

New required fields: `execution`, `relations`
New optional fields: `evidence[].metadata`, `evidence[].artifactType`
Updated: `claims[].supportedBy`, `coverage.evidence`, `coverage.relations`, `coverage.claims`

## 13. Conformance Test Changes

### New conformance cases (v0.4)

| Case | Description |
|------|-------------|
| `v0.4-basic` | Minimal valid v0.4 proof with execution, 1 evidence, 1 relation, 1 claim |
| `v0.4-full` | Complete proof with all relation types, multiple claims |
| `v0.4-empty-relations` | Valid: no relations (v0.4 allows empty) |
| `v0.4-orphan-evidence` | Invalid: evidence node with no incoming relation |
| `v0.4-unsupported-claim` | Invalid: claim with no `supports` relation |
| `v0.4-cycle-relations` | Invalid: circular dependency in relations |
| `v0.4-mismatched-binding` | Invalid: binding root doesn't include relations/claims |
| `v0.4-v3-compat` | Valid: v0.3 proof verified by v0.4 verifier |
| `v0.4-claim-fail` | Valid: claim with status "fail" (evidence contradicts) |

## 14. Implementation Order

1. **Schema definition** — `model/v2.go` with v0.4 types
2. **Backward compat layer** — `verifycore/compat.go` for v0.3 proof handling
3. **Binding v2** — Updated Merkle computation with relations + claims
4. **Signature v2** — Updated commitment digest
5. **Collectors** — Update evidence collectors to populate relations
6. **Claims engine** — Evaluate claims against evidence
7. **CLI updates** — inspect, claims, explain, graph
8. **WASM** — Update WASM verifier for v0.4
9. **Conformance** — Add v0.4 test cases
10. **Tests** — Unit + integration + conformance

- **Sigstore/GitHub Attestation adapters** → v0.6
- **SDK/Integration layer** → v0.6
